## 🩺 문제 정의

혈액투석 환자는 매 끼니마다 단순히 저염식 여부만 확인하는 것이 아니라
**열량·단백질·칼륨(K)·인(P)·나트륨(Na)**을 함께 고려해야 합니다.

한 영양소를 줄이기 위한 조정이 다른 영양소의 부족이나 초과로 이어질 수 있어,
환자는 결국 식사 전마다 **"무엇을 얼마나 먹어야 하는지"** 판단해야 합니다.

실제로 신장병 환자 커뮤니티에는 이런 어려움이 그대로 드러납니다.

> "식이요법이 힘드네요 ㅠㅠ" · "신장병 환자 식이요법 어떻게 하시나요?" ·
> "저염식하기 어렵습니다, 저염 식단 예시 좀 알려주세요" ·
> "단백질, 칼륨, 인 조절이 너무 어려워요"
> <sub>— 신장병 관련 네이버 카페</sub>

기존 식이관리 서비스가 섭취 후 기록과 영양정보 확인에 집중했다면,
FOOK은 다음 질문에서 출발했습니다.

> **먹은 뒤 확인하는 것이 아니라, 먹기 전에 기준에 맞는 한 끼를 만들 수 없을까?**

## 💡 Solution

FOOK은 사용자의 신체정보와 식사기록을 바탕으로 개인별 영양 기준을 설정하고,

**원하는 메뉴 선택 → AI 식단 생성 → 영양 기준 판정 → 자동 재조정 → 맞춤 레시피 제공**

과정을 하나의 서비스로 연결했습니다.

검토한 기존 식이관리 서비스는 섭취 후 기록이나 영양정보 확인을 중심으로 제공하고
있었습니다. FOOK은 사용자가 실제로 어려워하는 지점 — **식사 전에 메뉴와 양을 정하는 순간** — 에
집중해, 원하는 메뉴를 먼저 선택하게 하고 그 메뉴를 개인 영양 기준 안에서 실제로 먹을 수
있는 한 끼로 재구성하는 경험을 설계했습니다. 정보를 알려주는 데서 끝나지 않고, **오늘 이
메뉴를 이렇게 먹으면 된다는 실행 가능한 결과**를 주는 것이 목표입니다.

## 🧭 주요 기획 판단

FOOK을 만들면서 몇 가지 방식을 두고 판단해야 했습니다.
기술을 어떻게 썼는지보다, **왜 그 방식을 선택했는지**를 정리했습니다.

### 판단 1. 사진 인식보다 사용자의 메뉴 선택을 먼저 받음

FOOK은 무엇을 먹었는지 알아맞히는 서비스가 아니라, 재료와 중량을 기준으로 영양소를
계산하고 기준에 맞게 조정하는 서비스입니다. 식사 사진만으로는 실제 재료 구성과 섭취
중량을 정확히 추정하기 어렵다고 판단해, 사진 기반 추정 대신 **사용자가 먹고 싶은 메뉴나
가진 재료를 직접 선택**하도록 설계했습니다. 서비스가 계산에 필요로 하는 재료와 중량
정보를 보다 직접적으로 확보할 수 있는 입력 방식을 선택한 것입니다.

### 판단 2. 먹은 뒤 기록보다 먹기 전 결정을 지원

검토한 기존 식이관리 서비스는 영양정보 확인이나 섭취 후 기록을 중심으로 제공하고
있었습니다. 하지만 사용자는 결국 식사 전에 "오늘 무엇을 얼마나 먹을 것인가"를 다시
판단해야 합니다. FOOK의 핵심 경험을 사후 기록이 아니라, **식사 전 한 끼를 구성하고 기준에
맞게 재조정하는 과정**에 두었습니다.

### 판단 3. 필요한 기능을 구현하기 위해 관련 연구를 탐색

"사용자가 원하는 메뉴를 최대한 유지하면서 영양 기준을 만족하는 한 끼를 만들려면 어떻게
구현해야 할까"라는 질문에서 시작해 관련 연구를 찾았습니다. 식단 생성에는 teacher-forced
Seq2Seq와 REINFORCE로 영양 기준 충족도를 높이는 선행 연구(Lee et al., *Diet planning with
machine learning*, KDD 2021)를, 재료 대체에는 문맥 임베딩과 KNN으로 대체재를 찾는 선행
연구(Pellegrini et al., *Exploiting Food Embeddings for Ingredient Substitution*, HEALTHINF
2021)를 검토했습니다.

두 방식 모두 그대로 가져다 쓰지 않고 FOOK의 조건에 맞게 다시 구성했습니다 — 생성 모델은
한국어 식단 데이터로 다시 학습하고 투석 5대 영양소 기준으로 보상을 새로 설계했습니다.
재료 대체는 영어 BERT를 한국어 KLUE-BERT로 바꾸고 칼륨·인 임상 기준 필터를 새로 추가해,
**대체 후보 사전을 구축**하는 데 활용했습니다 — 서비스가 실행 중에 임베딩 모델을 직접
호출하는 것이 아니라, 이렇게 미리 만들어둔 사전을 조회하는 방식으로 동작합니다.

### 판단 4. 모델 정확도 하나가 아니라 '서비스 성공'을 평가

생성 모델이 정답에 가까운 메뉴를 예측했는지보다, 사용자에게는 (1) 영양 기준을 실제로
만족했는지 (2) 요청한 메뉴·재료가 유지됐는지 (3) 최종적으로 추천 가능한 한 끼가
만들어졌는지 (4) 재료 구성과 조리가 현실적인지가 중요하다고 판단했습니다. 그래서 120개
시나리오에서 이 네 가지를 각각의 지표로 나눠 평가하고, 별도로 식품영양학 박사의 전문가
검토를 더했습니다(자세한 수치는 아래 "검증 결과" 참고). **평가 기준 자체를 서비스가 실제로
줘야 하는 가치에서 거꾸로 설계**했습니다.

## 🤖 AI · RULE · LLM

FOOK은 모든 판단을 하나의 AI 모델에 맡기지 않고,
**생성·검증·설명의 역할을 분리**했습니다.

```text
사용자 조건 · 요청
        │
        ▼
AI 식단 생성
Seq2Seq + Attention
        │
        ▼
5대 영양소 기준 판정
        │
        ▼
RULE 기반 재조정
메뉴 · 재료 · 중량 보정
        │
        ▼
최종 영양 기준 재검증
        │
        ▼
LLM 레시피 재구성
        │
        ▼
맞춤형 한 끼 제공
```

| 영역       | 역할                                |
| -------- | --------------------------------- |
| **AI**   | 다양한 식사 데이터를 기반으로 한 끼 메뉴 조합 생성     |
| **RULE** | 영양 기준에 따라 초과·부족 여부를 판정하고 재료·중량 보정 |
| **LLM**  | 확정된 메뉴·재료·중량을 바탕으로 조리과정 작성        |

영양 수치와 적합성 판정을 LLM에게 맡기지 않고,
**계산 가능한 영양 기준은 코드로 검증하고 LLM은 조리 텍스트 생성에 활용**했습니다.
계산·검증과 생성의 역할을 분리해, 각 방식의 강점을 서비스 흐름에 맞게 활용했습니다.

## 🎛️ 영양 검증·보정 구조

AI가 생성한 식단이 처음부터 모든 기준을 충족하지 않을 수 있기 때문에
생성 결과를 다시 계산하고 단계적으로 보정합니다.

```text
식단 생성
   ↓
5가지 영양 기준 확인
   ↓
기준 미충족
   ↓
메뉴 · 재료 · 중량 조정
   ↓
영양성분 재계산
   ↓
최종 기준 확인
```

주요 보정 대상은 다음과 같습니다.

* 김치 및 고나트륨 식품 조정
* 조미료 나트륨 감량
* 고칼륨 식재료 및 섭취량 조정
* 고인 식품 조정
* 단백질 부족·초과 보정
* 열량 부족 보완

한 영양소의 조정이 다른 영양소에 미치는 영향을 고려해
**영향 범위에 따라 보정 순서를 설계**했습니다.

| ---------------- | ----------: |
| 5가지 영양 기준 충족률    |   **90.8%** |
| 사용자 지정 메뉴·재료 반영률 |   **94.7%** |
| 최종 식단 추천 성공률     |   **89.2%** |

별도로, 서로 다른 체중·메뉴·재료 조건으로 생성한 대표 식단 8개를 식품영양학 박사 1인이
검토했습니다(**평균 4.2 / 5**). 120개 시나리오 정량 평가와 전문가 정성 평가는 서로 다른
평가입니다 — 정량 평가는 영양 기준 충족·반영률·추천 성공 여부를 계산으로 판정하고, 전문가
평가는 메뉴 조화·식재료 반복·조리 현실성처럼 계산으로 판정하기 어려운 부분을 사람이
검토합니다.

> "모든 식단이 영양 기준을 충족하여 제공 적합성에는 문제가 없었습니다. 전반적으로
> 기계 생성의 이질감은 크지 않았으나, 일부 메뉴 구성에서는 실무 경험이 충분히
> 반영되지 않은 점이 확인되었습니다."
> <sub>— 식품영양학 박사</sub>

전문가 검토에서는 대표 식단 8개 모두 영양 기준을 충족했으며,
일부 메뉴 조화·식재료 반복·조리 현실성은 추가 개선 영역으로 확인했습니다.

해당 프로젝트는 **2026 K-디지털 트레이닝 해커톤에서 장려상(고용노동부 장관상)을
수상**했습니다.

## 🌱 서비스 도입·확장 가설

FOOK은 이번 프로젝트에서 **서비스 구현과 결과 검증까지**를 목표로 진행했습니다.
아래는 실제 도입 사례가 아니라, 앞으로 검토해볼 수 있는 방향을 정리한 가설입니다.

### 초기 사용자

* 혈액투석 환자
* 보호자

### 도입 가능 주체 (검토 대상)

* 투석 병·의원
* 영양관리·건강관리 기관
* 디지털 헬스케어 서비스 제공 주체

### 도입 시나리오 (향후 검토 가능한 운영 방식)

의료진·영양사가 개인별 영양 기준을 설정하고 → 환자가 일상에서 FOOK으로 식단을
생성·기록하고 → 축적된 식사 기록을 이후 상담에서 참고하는 흐름을 가정할 수 있습니다.
**실제로 병·의원에서 이 방식으로 운영해 본 적은 없으며, 향후 검토가 필요한
시나리오입니다.**

### 사업모델 가설

개인이 직접 이용하는 B2C 방식 외에, 기관이 서비스를 도입하고 환자가 사용하는 B2B2C
방식도 하나의 사업화 가설로 검토할 수 있습니다. 현재 프로젝트에서는 서비스 구현과
결과 검증을 우선했으며, **실제 기관 도입과 수익모델은 추가 검증이 필요한
가설입니다.**

### 확장 가능성

FOOK은 '질환별 영양 기준 → 식단 생성 → 기준 검증 → 재조정'이라는 구조로 돼 있어,
당뇨·고혈압 등 다른 만성질환의 영양 기준을 적용하는 방식으로 확장을 검토할 수
있습니다. 다만 이는 아직 검증되지 않은 방향이며, 질환별로 별도의 영양 기준 설계와
검증이 필요합니다.

## 🛡️ 안전성·보안 및 오류 대응

### 계정·사용자 데이터 보호

* 계정·신체정보·식사기록 등 서비스 제공에 필요한 정보를 저장하며, **혈액검사 결과나 병원 의료정보는 직접 연계하지 않습니다.**
* 비밀번호는 **PBKDF2-SHA256 + Random Salt**로 해싱하고 세션 토큰도 Hash 형태로 저장합니다.
* 사용자 데이터는 인증된 계정별로 분리하며, API Key·DB 접속정보는 환경변수로 관리하고 Repository에서 제외합니다.

### 식이 정보 안전성

* **식단 생성·영양 검증과 LLM 레시피 생성을 분리**해 LLM이 영양 적합성을 직접 판단하지 않도록 설계했습니다.
* 재료·중량 조정 후 5대 영양소를 다시 계산하며, 기준을 충족하지 못하면 **미충족 항목과 주의사항을 함께 안내**합니다.

### 시스템 오류 대응

* 서버 지연·연결 실패 시 Timeout과 상황에 맞는 오류 안내를 제공합니다.
* 서버 저장 실패 시 식사기록 등은 **현재 브라우저에 임시 보존**해 일시적인 연결 오류로 데이터가 바로 사라지지 않도록 했습니다.
* AI 생성 모델의 동시 요청 오류를 방지하기 위해 **Lock과 초기 Warm-up**을 적용했습니다.

## ⚠️ 서비스 범위 및 한계

FOOK은 혈액투석 환자의 식사 결정을 돕기 위한 **식이관리 프로토타입**입니다.

* 의료진의 진단이나 처방을 대체하지 않습니다.
* 실제 혈액검사 수치를 직접 반영하지 않습니다.
* 기본 영양 기준은 신체정보를 기반으로 산출하며 사용자가 별도 목표값을 설정할 수 있습니다.
* 개인의 검사 결과와 치료 상태에 따라 적절한 식이 기준이 달라질 수 있으므로 실제 식이요법은 담당 의료진 또는 임상영양사와의 상담이 필요합니다.
