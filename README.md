## 🩺 왜 만들었나요?

혈액투석 환자는 **열량·단백질·칼륨(K)·인(P)·나트륨(Na)** 다섯 가지 영양소를 매 끼
동시에 지켜야 합니다. 문제는 이 다섯이 서로 얽혀 있다는 점입니다 — 칼륨을 낮추려고
채소를 줄이면 단백질이 무너지고, 열량을 채우려고 간식을 더하면 인이 넘칩니다. 사람이
손으로 다섯 개를 동시에 맞추기는 매우 어렵습니다.

실제로 신장병 관련 환자 커뮤니티에는 이런 어려움이 그대로 드러납니다.

> "식이요법이 힘드네요 ㅠㅠ" · "신장병 환자 식이요법 어떻게 하시나요?" ·
> "저염식하기 어렵습니다, 저염 식단 예시 좀 알려주세요" ·
> "단백질, 칼륨, 인 조절이 너무 어려워요"
> <sub>— 신장병 관련 네이버 카페</sub>

정작 "이 끼니를 얼마나 먹어야 기준 안에 드는지"까지 계산해주는 서비스는 찾기
어려웠습니다. 대부분의 식단 추천 서비스는 일반인 권장량 기준으로 메뉴 조합만 제안하고
끝납니다. KOOK은 여기서 한 단계 더 들어가 **개인 기준을 세우고 → AI가 한 끼를 만들고
→ 기준을 넘으면 재료 단위까지 스스로 고치는** 서비스를 만들었습니다.

## 🤖 AI 시스템은 어떻게 동작하나요?

```
데이터
  ↓
재료 대체
  ↓
식단 생성
  ↓
영양 기준 검증
  ↓
재료·중량 재조정
  ↓
최종 재검증
  ↓
레시피 재구성
```

각 단계를 기술적으로 풀면:

| 단계 | 기술 |
|:---|:---|
| 재료 대체 | KLUE-BERT 임베딩 + KNN(Annoy)로 저칼륨·저인 대체 재료 후보 탐색 |
| 식단 생성 | Seq2Seq(GRU Encoder–Decoder) + Bahdanau Attention으로 밥·국·반찬 시퀀스 생성 |
| 영양 기준 검증 | 5대 영양소 × 목표 범위 대조 |
| 재료·중량 재조정 | 7단계 레버로 메뉴 교체·섭취량(g) 조정 (바로 아래 "핵심 AI/알고리즘" 참고) |
| 최종 재검증 | 재조정 후 영양성분 다시 계산, 통과할 때까지 반복 |
| 레시피 재구성 | 재조정된 재료·양에 맞춰 LLM이 조리법 재작성 |

생성 단계는 REINFORCE로도 보정됩니다: 영양 기준 통과율과 사용자가 지정한 메뉴·재료가
얼마나 보존됐는지를 함께 보상으로 줘서, 처음부터 기준에 가까운 조합이 나오도록
학습시켰습니다.

<details>
<summary>🔬 보상 함수 상세</summary>

```
보상 = 영양 기준 통과율 × (0.5 + 0.5 × 최종 보존율)

영양 기준 통과율 = 통과한 영양 기준 수 / 5
개별 보존율      = 1 − min(1, 총 그램 변화량 / 조정 전 총 그램)
최종 보존율      = 0.7 × 유저 지정 메뉴 보존율 + 0.3 × 전체 식단 보존율
```

기준을 다 지켜도 사용자가 고른 메뉴·재료가 원형을 잃으면 보상이 깎이도록 설계해,
"기준은 맞지만 전혀 다른 음식"이 되는 걸 막았습니다.

</details>

## 🧠 핵심 AI / 알고리즘

이 프로젝트의 핵심입니다. AI가 만든 한 끼가 기준을 넘으면, **7개의 레버를 정해진 순서로 당겨** 기준 안으로 넣습니다.

> 순서가 중요합니다. 칼륨을 먼저 낮추면 단백질이 무너지고, 열량을 먼저 채우면 인이 넘칩니다.
> **영향 범위가 좁은 것부터** 당기도록 순서를 고정했습니다.

| 순서 | 레버 | 하는 일 |
|:---:|:---|:---|
| 1 | `lever_kimchi` | 김치를 저염·저칼륨 종류로 교체 (나트륨·칼륨 동시 감소) |
| 2 | `lever_sodium` | 양념 나트륨 감량 |
| 3 | `lever_sodium_extra` | 1·2로 부족하면 추가 감량 |
| 4 | `lever_potassium` | 고칼륨 메뉴 교체 · 채소 섭취량 조정 |
| 5 | `lever_phosphorus` | 고인 메뉴 교체 · 섭취량 조정 |
| 6 | `lever_protein` | 단백질을 목표 범위 안으로 |
| 7 | `lever_calorie` | 남은 열량을 간식으로 채움 |

### 두부·콩류 전용 경로 (개선 작업)

두부·콩류를 지정하면 문제가 있었습니다. 식물성 단백질은 **인 함량 대비 흡수율이 낮은데**, 기존 레버는 총 인만 보고 양을 과하게 깎았습니다. 그래서 조건부 경로를 추가했습니다.

| 함수 | 역할 |
|:---|:---|
| `_plant_protein_path_needed` | 두부·콩류 앵커인지 판정해 경로 분기 |
| `lever_phosphorus_rawP` | 흡수율을 반영한 인 기준으로 재계산 |
| `lever_protein_capped` | 단백질 조정 시 열량 상한(90%)을 함께 준수 |
| `lever_calorie_capped` | 열량 보충 시 인 상한을 넘지 않도록 제한 |

**검증 결과 — 3,600회 페어 실행**

| 항목 | 개선 전 | 개선 후 |
|:---|:---:|:---:|
| 두부·콩류 성공률 | 94% | ✅ **100%** |
| 후보 0개(생성 실패) | 6% | ✅ **0%** |
| 비현실적 섭취량 발생 | 46% | ✅ **20%** |
| 어육류 결과 변화 | — | ✅ **2,400건 전부 동일 (회귀 없음)** |

> 13단계 진단→해결 전 과정은 [`model-development/generation-model_seq2seq-rl/research-log/phosphorus-protein-resolution/`](model-development/generation-model_seq2seq-rl/research-log/phosphorus-protein-resolution/ADOPTION_REPORT.md)에 남겨뒀습니다.

<details>
<summary>🔬 검증했지만 아직 배포하지 않은 것 — 국(soup) 다양성 개선</summary>

같은 앵커·같은 seed로 여러 번 생성하면 국이 소수 메뉴로 쏠리는 현상을 발견해 원인을 추적한 결과,
디코더가 seed 시퀀스의 국 위치 토큰을 그대로 베끼는 구조적 shortcut이었습니다. 국 슬롯을 100%
마스킹하고 재학습(C_mask100) + RL 재학습까지 마치자 국 고유 종류가 **4.1개 → 28.6개(7배)**로
늘면서 영양 충족률도 오히려 개선(68.8% → 97.6%)됐습니다.

다만 이번 세션 범위에서는 체크포인트 교체(배포)까지는 진행하지 않아, 현재 서비스는 여전히 이
개선 이전 체크포인트를 쓰고 있습니다. 전체 진단·실험 과정은
[`research-log/soup-diversity-masking/`](model-development/generation-model_seq2seq-rl/research-log/soup-diversity-masking/FINDINGS.md)에 정리해뒀습니다.

</details>

### 영양 상담 RAG 챗봇

> ⚠️ 백엔드 API(`POST /chat`)로 구현·배포까지 돼 있지만, **프론트엔드 화면에는 아직
> 연결하지 않았습니다.** 지금 배포된 서비스에서는 이 기능을 직접 써볼 수 없습니다.

식단 생성과 별개로, "말린 바나나 먹어도 되나요?" 같은 자유 질문에 답하는 챗봇(`FOOK_rag_chatbot.py`,
`POST /chat`)을 만들었습니다. 질문 두 종류를 구분해서 처리합니다.

| 질문 유형 | 처리 방식 |
|:---|:---|
| 특정 재료의 섭취 가능 여부 | **영양DB 직접 조회.** 100g당 칼륨/인 → 1회 섭취 기준량으로 환산해 저/중/고칼륨 등급 판정. 오늘 먹은 양(`consumed`)을 같이 주면 남은 예산과 비교까지 |
| 일반 지식 질문 ("왜 위험한가요?" 등) | **RAG.** 대한신장학회 등 자료를 임베딩한 지식베이스에서 유사 근거를 찾아 답변, 근거 없는 내용은 "확인할 수 없다"고 답함(추론 금지) |

숫자 판정은 코드가 확정하고 LLM은 그 결론을 설명하는 문장만 담당하도록 프롬프트와 후처리를
분리했습니다 — 실측 중 LLM이 코드가 이미 계산한 판정을 스스로 다시 비교하다가 뒤집어 말하는
사례를 발견해서, 최종 결론 문자열을 코드가 답변 끝에 못박는 이중 안전장치를 넣었습니다.

## 🔄 프로젝트 종료 후 개인 개선

팀 프로젝트 종료 후에도 서비스를 개인적으로 유지하며,
실제 배포 환경을 기준으로 구조·안정성·사용성을 추가 개선했습니다.

### 1. `/generate_day` 동시성 레이스 컨디션

**문제**: 배포 후 `/generate_day`가 간헐적으로 500 에러를 반환했습니다.

**원인**: 식단 생성에 쓰는 TF 모델(`gen`)은 전역으로 공유되는 객체인데, FastAPI가 동기
엔드포인트를 스레드풀에서 병렬 실행하다 보니 동시 요청이 같은 모델 객체의 GRU 셀
지연 초기화(lazy weight build)에 동시에 접근해 레이스 컨디션이 발생했습니다
(`'GRUCell' object has no attribute 'kernel'`).

**개선**: 모델 호출 구간에 `threading.Lock()`을 걸고, 서버 기동 시 한 번 예열
호출(`gen_batch(n=2)`)을 넣어 지연 빌드가 단일 스레드에서 먼저 끝나도록 했습니다.

**검증**: 수정을 되돌려 로컬 8/9, 배포 환경 4/6 요청이 실패하는 것을 직접
재현했습니다. 수정을 다시 적용한 뒤 5라운드에 걸쳐 동시 요청 40/40을 통과시켜,
"한 번 돌려서 됐다"가 아니라 되돌리기→재현→재적용→재검증까지 인과관계로 확인했습니다.

### 2. API 보안 강화

**문제**: 로그인·비밀번호 재설정·LLM 엔드포인트(레시피 재구성·음성·챗봇)에 별도
방어가 없었고, `/health`는 DB 연결에 실패하면 예외 메시지를 그대로 응답에
노출했습니다.

**개선**: 새 의존성 추가 없이 IP 기준 슬라이딩 윈도우 rate limiter를 직접
구현했습니다(`backend/rate_limit.py`) — 로그인 5분 10회, 비밀번호 재설정 15분
5회, 레시피/음성/챗봇 각 5분 20회로 제한. CORS 허용 오리진을 와일드카드에서 실제
배포 도메인 + 로컬 개발 주소로 좁혔습니다. `/health`는 예외를 서버 로그에만 남기고
응답에는 `ok: false`만 돌려주도록 고쳐, DB 호스트·계정 정보가 새 나가지 않게
했습니다.

**검증**: rate limiter의 허용/차단/IP별 분리/윈도우 리셋 동작을 pytest로 검증하고,
CORS 허용·차단 여부를 로컬과 실제 배포 양쪽에서 curl로 확인했습니다.

### 3. `App.tsx` 대규모 리팩터링

**문제**: 화면 라우팅·상태·컴포넌트가 전부 `App.tsx` 한 파일(3,753줄)에 있어,
화면 하나를 고치려 해도 파일 전체를 뒤져야 했습니다.

**개선**: `pages/`(라우트별 화면) · `components/`(화면 간 공용 조각) · `hooks/` ·
`services/` · `utils/`로 분리했습니다. 상태 결합이 강한 화면 전환 로직(생성→판정→
재구성→비교→완성)은 한 덩어리로 옮기고, 나머지는 라우트 단위로 하나씩 옮기며 단계마다
빌드·클릭 검증 후 커밋했습니다.

**검증**: 각 단계마다 `npx tsc -b`, `npm run build` 통과와 브라우저 클릭 검증을
거쳤습니다. 최종적으로 `App.tsx`는 라우팅과 전역 상태 제공만 남아 150줄까지
줄었습니다.

### 4. 온보딩 화면 위치 어긋남

**문제**: 온보딩 1~5단계 화면의 "n/5" 배지와 제목 위치가 단계마다 미묘하게 어긋나
보인다는 피드백을 받았습니다.

**원인**: 처음엔 이미지 비율 차이로 진단해 캔버스 비율을 통일했지만 재현됐습니다.
실제 원인은 배지·제목 자체가 각 이미지 **안에 그림으로 그려져 있고**, 그 위치가
이미지마다(제작 시점에) 미세하게 달랐다는 것 — 이미지 비율을 맞추는 방식으로는
원천적으로 고칠 수 없는 문제였습니다.

**개선**: 텍스트를 이미지에 굽는 방식을 버리고, 제목·건너뛰기·배지를 전부 실시간
DOM 텍스트로 전환했습니다. 이미지는 실제 앱 화면 캡처만 담당합니다. 함께 발견한
`scrollbar-gutter: stable`이 스크롤이 필요 없는 화면에서도 오른쪽 여백을 고정
확보해 콘텐츠가 좌우 비대칭으로 보이던 문제도 같이 제거했습니다.

**검증**: 브라우저에서 1~5단계를 전부 재확인했습니다 — 배지·제목이 더 이상 이미지에
의존하지 않으므로 구조적으로 위치가 어긋날 수 없습니다.

```bash
git clone https://github.com/wouldu0/kook-hemodialysis-meal-ai.git
```

```env
DATABASE_URL=postgresql://...        # Neon Postgres 연결 주소
OPENAI_API_KEY=sk-...                # 레시피 재구성 · 음성 안내 · 영양 상담 챗봇용
```

> ⚠️ `.env`는 `.gitignore`에 등록되어 있습니다. **저장소에 올리지 마세요.**
> `OPENAI_API_KEY`가 없어도 서버는 뜹니다. 레시피 재구성·음성 안내·영양 상담 챗봇만 동작하지 않습니다.

**4️⃣ DB 테이블 생성** (최초 1회)
```bash
psql "$DATABASE_URL" -f sql/001_full_schema.sql
psql "$DATABASE_URL" -f sql/002_account_recovery.sql
```

**5️⃣ 백엔드 실행**
```bash
python -m uvicorn server_FOOK:app --port 8000
```
> 최초 기동 시 모델을 읽느라 10초쯤 걸립니다. `Application startup complete`가 뜨면 준비 완료입니다.
> API 문서는 http://127.0.0.1:8000/docs 에서 볼 수 있습니다.

> http://localhost:5173 으로 접속합니다. 개발 모드는 자동으로 로컬 백엔드(`127.0.0.1:8000`)를 사용합니다.

## ⚠️ 한계 및 향후 개선

- **의료진 처방을 대체하지 않습니다.** 생성된 식단은 참고용이며, 실제 식이요법은
  반드시 담당 의료진·임상영양사와 상의해야 합니다.
- **실제 혈액 검사 수치는 반영하지 않습니다.** 키·체중·성별 기반 표준 기준으로 목표를
  세우며, 개인의 실제 혈중 칼륨·인·나트륨 수치는 입력받지 않습니다.
- **전문가 평가에서 확인된 한계**: 8개 대표 식단 모두 영양 기준은 충족했지만, 메뉴
  조화·식재료 반복·조리 현실성 측면은 개선 여지가 있다는 의견을 받았습니다.
- **아이디/비밀번호 찾기는 데모 환경 기준의 간소화된 인증입니다.** 이메일·SMS 발송
  수단이 없어 이름+생년월일 확인만으로 처리합니다(비밀번호 자체는 PBKDF2-SHA256
  310,000회 + 랜덤 salt로 해싱, 세션 토큰도 해시로 저장). 무차별 대입 시도는 IP별
  rate limit(`/auth/login` 5분 10회, `/auth/reset-password` 15분 5회)으로 늦추지만,
  본인 확인 자체가 약하다는 한계는 남아있습니다. 실제 서비스로 운영한다면 이메일/SMS
  OTP 같은 별도 인증 수단이 필요합니다.
