## 1. 진단 환경

**사용 모델**: C_mask100 + RL(epoch 260)
**사용 checkpoint**: `results_rl_soupmask_FOOK/C_mask100_rl/checkpoints_best/ckpt-3`
**평가 규모**: 주찬앵커 3종 × seed 5개(사전등록 10개 중 앞 5개: 행11/12/6/36/7) × 조건당 30회 ×
회당 24후보 = **10,800개 후보** (screening 규모, 원인이 명확해 50회 확대 불필요했음)
**사용한 실제 make_meal() 코드**: `app_core_FOOK.py`의 `make_meal()`/`gen_batch()` 로직을 그대로
복제(로직·순서·기준 전부 원본과 동일, encoder/decoder만 C_mask100+RL 체크포인트로 교체 — 828vocab이라
`core.gen`(827vocab 전용)에 직접 못 꽂아서 복제가 불가피했음)
**게이트 실제 적용 순서**: 아래 §1.1 참고
**F.adjust() 반환값 확인 결과**: 아래 §1.2 참고

### 1.1 게이트 실제 적용 순서 (app_core_FOOK.py:393-410 코드 그대로)

```
S0  생성 직후 (gen_batch, 24후보)
S1  dup_today / clash / seafood_overload / high_p_overload 계산 — 전부 "원본(adjust 전) menus" 기준
S2  F.adjust() 적용(레버) → before, after, inst 획득
S3  unrealistic_reason(inst) 계산 — adjust 후 inst 기준
S4  passes(after, b) 계산(영양5종) — adjust 후 after 기준
S5  6개 조건(영양·현실성·dup_today·재료겹침·해산물과다·고인과다)을 동시에 AND 결합 → ok
S6  후보를 앞에서부터 훑다가 첫 ok=True 즉시 채택. 끝까지 하나도 없으면 부분점수 최고 채택
```

**★ 중요(사용자 요청대로 실제 순서를 정확히 기록)**: 원본 코드는 게이트가 "순차 필터"(살아남은
후보만 다음 게이트로 넘어감)가 아니다. dup_today·clash·overload·p_overload 4개는 F.adjust() **전**
원본 menus로 계산되고, unreal·passes 2개는 F.adjust() **후** 결과(inst/after)로 계산된 뒤, 6개를
**동시에 AND**로 합친다. 즉 "각 게이트를 통과한 후보만 다음 게이트로 넘어간다"는 카스케이드가
아니라, "같은 F.adjust() 결과 하나에 대해 6개 조건을 독립적으로 계산해서 마지막에 합친다"는 구조다.
이번 진단의 "게이트별 통과율"도 이 구조에 맞춰 **각 조건을 전체 후보 풀에 독립적으로 적용한 결과**로
계산했다(하나가 다른 것의 입력을 바꾸지 않음).

### 1.2 F.adjust() 반환값 (FOOK_adjust_levers.py:1111-1143에서 직접 재확인)

```python
def adjust(menus, b, anchor=None):
    ...
    return before, totals(inst), inst, p_ok
```

- **before**: 레버 적용 **전** 영양 총계(dict, `totals(원본 inst)`)
- **after**: 레버 적용 **후** 영양 총계(dict) — `passes(after, b)`가 실제 통과판정에 쓰는 값
- **inst**: 레버 적용 후 재료 인스턴스 리스트 — 메뉴명 치환·통째교체가 여기 반영됨.
  `unrealistic_reason(inst)`이 이 값을 봄
- **p_ok**: `lever_phosphorus` 자신이 보고하는 성공여부. **app_core는 이 값을 안 믿고**
  `passes(after, b)`로 직접 재검증한다(원본 코드 주석에 명시: "레버 말을 믿지 않고 최종 영양값을
  passes()로 직접 검사한다") — 이번 진단에서도 이 관례를 그대로 따름(p_ok는 참고용 컬럼으로만 기록)

이번 진단 코드는 `before, after, inst, p_ok = F.adjust(...)`로 명시적 unpacking했음(위치 인덱스
임의접근 없음).

## 2. 단계별 부찬 다양성

| 단계 | 고유 부찬 수 | Top-1 비율 | entropy | 생존율 |
|---|---|---|---|---|
| S0 생성 직후 | 84 | 27.9% | 3.93 | 100% |
| S2 F.adjust() 후 | **94**(증가) | **14.7%**(감소) | **4.64**(증가) | 100% |
| S9 모든 게이트 통과(생존) | 48 | 16.0% | 4.31 | **11.2%** |
| S10 최종 선택 | 44 | 17.8% | 4.42 | 4.2% |

**S0→S2(레버/F.adjust() 영향)**: 다양성이 줄지 않고 오히려 **늘어난다**(고유84→94, entropy
3.93→4.64, top1비율 27.9%→14.7%로 감소). 레버가 부찬을 다양한 대체재로 흩어놓는 효과.

**S2→S9(게이트 통합 영향)**: 여기서 가장 크게 줄어든다(고유94→48, -49%, 생존율 11.2%). 6개
게이트 중 어디가 이 감소의 대부분을 차지하는지는 §3 참고.

**S9→S10(최종선택 영향)**: 고유48→44로 소폭 감소하지만 entropy는 오히려 4.31→4.42로 **증가**.
최종선택(첫통과 즉시채택) 자체가 다양성을 추가로 크게 깎지는 않는다.

### 앵커별 차이(중요 — 앵커마다 병목 지점이 다름)

| 단계 | 생선구이 | 육류 | 두부콩류 |
|---|---|---|---|
| S0 top1비율 | 30.3% | **83.8%**(!) | 23.6% |
| S0 entropy | 3.34 | **1.31**(매우낮음) | 3.95 |
| S2 top1비율 | 30.3%(불변) | **14.0%**(급감) | 21.3% |
| S2 entropy | 3.62 | **3.56**(급증) | 4.30 |
| S9 entropy | 3.09 | 3.58 | 3.71 |
| S10 entropy | 2.91 | 3.49 | **4.07** |

**육류(제육불고기) 조건은 생성 단계(S0)부터 이미 극도로 편중**(상추겉절이 83.8%, entropy 1.31 —
지난번 국 슬롯에서 본 "생성단계 편중"과 같은 종류의 현상). 그런데 이 조건에서 F.adjust()가
그 편중을 거의 다 풀어준다(83.8%→14.0%, entropy 1.31→3.56). 반대로 생선구이 조건은 S0→S2에서
top1비율이 전혀 안 변함(30.3%→30.3%) — 레버가 이 조건에서는 부찬을 거의 안 건드린다는 뜻.

## 3. 가장 큰 병목

**후보를 가장 많이 탈락시키는 게이트**: `nutrition_all_pass`(영양5종) — **탈락률 73.8%**
(2위는 `reality_pass` 42.1%)

**부찬 다양성을 가장 크게 줄이는 게이트**: **역시 `nutrition_all_pass`** — 고유손실 31개(전체
손실의 대부분), entropy손실 0.34(6개 게이트 중 최대), top1비율 +3.2%p 증가(최대). 이번 케이스는
"가장 많이 탈락시키는 게이트"와 "다양성을 가장 크게 줄이는 게이트"가 **일치**한다.

| 게이트 | 탈락률 | 고유손실 | entropy손실 | top1증가 |
|---|---|---|---|---|
| **nutrition_all_pass** | **73.8%** | **31** | **0.34** | **3.2%p** |
| reality_pass | 42.1% | 16 | 0.12 | 1.6%p |
| duplicate_pass(재료겹침) | 13.3% | 3 | 0.06 | 0.9%p |
| seafood_overload_pass | 12.5% | 4 | 0.00 | 2.1%p |
| dup_today_pass | 0.0%(구조적, 하루연속 아님) | 0 | 0 | 0 |
| high_p_overload_pass | 0.0%(부찬에서 거의 안 걸림) | 0 | 0 | 0 |

**최종 선택 편향 여부**: 미미함. S9→S10에서 고유수는 소폭 감소(48→44)하지만 entropy는 오히려
증가(4.31→4.42) — "첫 통과 즉시 채택" 로직 자체가 특정 부찬으로 쏠리게 만드는 주범은 아니다.

**레버/F.adjust() 영향 여부**: **오히려 다양성을 개선하는 방향**(§2 참고) — 병목이 아니라
완충 역할을 하고 있음. 단, 조건(앵커)에 따라 개입 정도가 크게 다름(육류 조건에서만 강하게 개입).

## 4. 메뉴별 원인

**반복 선택되는 부찬(생성빈도 낮은데 선택률 과도)**: 올방개묵무침(3회생성/2회선택=66.7%),
물미역초무침(6/2=33%), 치킨가라아게(4/1=25%), 차돌박이숙주볶음(15/3=20%), 미트볼조림(71/10=14.1%).
**반복 선택되는 이유**: 표본이 워낙 작아(3~15회) 우연(소표본 노이즈)일 가능성이 크고, 영양값
(P/K/Na)만 봐서는 이들이 "특별히 안전한" 조합이라 보기 어려움(탈락한 메뉴들과 수치 범위가 겹침) —
**대신 이 메뉴들 상당수가 레버의 대체재 풀(예: 저인·저칼륨 스왑 타깃)의 "도착지"로 자주 쓰이는
아이템일 가능성이 있음**(§6 추가확인 참고, 코드 확인까지는 이번 범위에서 못 함).

**생성되지만 탈락하는 부찬(상위)**: 숙주나물(1584회생성/80선택=5.1%), 취나물무침(855/18=2.1%),
애호박나물(772/34=4.4%), 쑥갓두부무침(591/7=1.2%), 새송이버섯볶음(449/29=6.5%).
**주요 탈락 이유**: 전부 `most_common_failure_gate = nutrition`(영양게이트). 평균 인(P)이
327~358mg, 칼륨 570~820mg 수준으로 특별히 극단적이진 않음 — 개별 재료 자체보다는 **다른 슬롯
(주찬·국·밥)과 합쳐졌을 때 5개 기준(특히 열량·단백질) 동시충족이 어려운 조합**일 가능성이
높음(이번 진단은 영양소별 세부 탈락원인까지는 분해 안 함 — §6 한계 참고).

**특이 케이스 — 항상 치환되는 메뉴**: **상추겉절이**(생성 3017회, 선택 0회, 실패게이트 기록 자체가
없음 = 매번 F.adjust()가 다른 이름으로 바꿔버려서 원래 이름으로는 살아남는 경우가 아예 없음)와
**배추김치**(생성 695회, 선택 0회, 동일 패턴). 이 둘은 "생성은 많이 되지만 영양 때문에 탈락"이
아니라 **레버가 100% 확률로 다른 메뉴로 갈아치우는** 케이스 — 육류 조건 S0의 83.8% 편중이 바로
이 상추겉절이였고, 레버가 이걸 거의 항상 치환하면서 S2 다양성이 늘어난 것과 정확히 맞물림.

**앵커별 차이**: 육류 조건만 생성단계부터 심하게 편중(상추겉절이 83.8%) — 국 슬롯에서 봤던
"특정 앵커에서 생성모델 자체가 이미 결정론적"인 것과 같은 계열의 현상. 생선구이·두부콩류는
생성단계는 비교적 다양하고, 병목이 전부 nutrition 게이트(S2→S9)에 몰려있음.

## 5. 최종 원인 판정

**부찬 편향의 주원인**: **③ 영양 게이트(nutrition_all_pass)가 다양성 병목** — 전체 손실(고유
94→48)의 대부분을 이 게이트 하나가 차지함(탈락률 73.8%, 다른 5개 게이트 전부 합쳐도 이만큼 안 됨).

**부원인**: **① 모델 생성 단계 편향(육류 조건에 한정)** — 다른 두 앵커는 생성단계가 다양한데
육류 조건만 S0부터 83.8%로 편중돼있음. 단, 이건 F.adjust()가 상당부분 상쇄해줘서(83.8%→14.0%)
최종 다양성엔 영양게이트보다 영향이 작음.

**모델 생성 단계 문제 여부**: 있음, 단 육류 조건 한정. 국 슬롯 문제(seed 복사)와는 별개의
현상으로 보임(부찬은 seed 위치가 아니라 앵커-조건부 편향이라 원인 메커니즘이 다를 수 있음 —
이번 진단 범위 밖).

**F.adjust()/레버 문제 여부**: 아니오 — 오히려 다양성을 개선하는 쪽으로 작동함. 단, "상추겉절이·
배추김치는 100% 치환됨"이라는 특이 패턴은 레버의 **대체재 풀이 특정 소수 메뉴로 수렴하는 구조**일
가능성을 시사함(6번 추가확인 항목, 코드 확인은 이번 범위 밖).

**게이트 문제 여부**: **있음, 주원인**. nutrition_all_pass가 압도적.

**최종 선택 문제 여부**: 경미함. tie-break나 후보 정렬 순서에 의한 명백한 편향 증거는 못 찾음
(S9→S10 entropy가 오히려 증가).

이 진단은 **판정 기준 3번**("특정 개별 게이트 전후 entropy와 고유종류가 크게 감소 → 해당 게이트가
다양성 병목")에 정확히 해당하고, 부분적으로 **1번**("S0부터 top1 비율이 높고 entropy가 낮음 →
모델 생성 단계 편향")도 육류 조건에 한해 해당함.

- **변경 내용**: 상추겉절이·배추김치가 왜 항상 걸리는지(어느 레버의 어느 조건에서 트리거되는지),
  대체재 풀이 몇 개나 되는지 확인
- **기대효과**: "드물게 생성되지만 과도하게 선택되는" 그룹(올방개묵무침 등)이 레버의 좁은 대체재
  풀 도착지인지 확정
- **영양 성능 위험**: 없음(읽기 전용 조사)
- **다양성 개선 가능성**: 만약 대체재 풀이 실제로 좁다면, 풀을 넓히는 게 부찬 다양성 개선의
  직접적 레버가 될 수 있음(이번엔 제안만, 적용은 별도 승인 후)
- **가장 작은 코드 변경안**: 없음(조사만)
- **검증 방법**: 상추겉절이가 걸리는 레버 함수에 로그 추가해 어떤 대체재로 몇 종류나 바뀌는지 카운트

### 제안 3: 육류 앵커 조건의 생성단계 편중(83.8%) 원인 조사 — 국 슬롯 진단과 동일 방법론 재사용
- **변경 위치**: 없음(진단만, `diagnose_soup_seed_dependency_FOOK.py` 방법론을 부찬에 적용)
- **변경 내용**: 육류(제육불고기) 앵커일 때 부찬 확률분포 자체가 이미 편중된 건지, seed의 다른
  슬롯(밥·국·김치)과의 상관관계 때문인지, 국 슬롯 때처럼 seed 자체를 베끼는 건지 확인
- **기대효과**: 부찬도 국처럼 "seed 복사형" shortcut이 있는지, 아니면 임상적으로 타당한
  앵커-부찬 연관(제육볶음→쌈채소는 실제로도 흔한 조합)인지 구분
- **영양 성능 위험**: 없음(진단만)
- **다양성 개선 가능성**: 만약 shortcut이면 국처럼 마스킹으로 개선 여지 있음. 만약 임상적으로
  타당한 패턴이면 "문제"가 아니라 "정상"이므로 손대면 안 됨 — 이 구분이 핵심
- **가장 작은 코드 변경안**: 없음(조사만)
- **검증 방법**: seed 5개를 다르게 고정하고 육류 앵커의 부찬 분포가 seed마다 다른지 확인(같으면
  앵커-조건부 학습패턴, seed 따라 바뀌면 seed shortcut)

**우선순위**: nutrition 게이트가 압도적 병목이므로 **제안1(영양소별 분해)을 최우선**으로 하고,
그 다음 제안2(대체재 풀), 제안3(육류 조건 원인)은 병행 가능.
