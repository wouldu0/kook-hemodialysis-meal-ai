메타 노트(먼저 읽기): 이 리포트는 이전 세션에서 크래시한 백그라운드 에이전트가 남긴

## Rewrite 전략

문항당 최대 2개, 패턴 B(도메인-프리픽스 재구성)/C(임상 동의어 치환)/D(제네릭 수량·빈도
접미사) 세 가지만 사용. 스크립트 코멘트(라인 158-168, 325-336)에 전략 설계 이유가
명시돼 있고, 각 rewrite 딕셔너리 항목에 `reasoning` 필드로 근거가 개별 기록돼 있음을
JSON에서 직접 확인했다(7문항×2 rewrite = 14개 전부 `reasoning` 비어있지 않음).

- **근거 로깅 상태**: 사후 답변 텍스트를 역설계한 게 아니라 사전에 근거가 기록돼 있다.
  itch1의 C-패턴("소양증")은 rewrite 작성 *전에* `grep 소양증 data/rag-source/*.txt`로
  KB 본문에 실제 존재함을 확인했고, 그 확인 지점이 itch1 자신의 정답 청크(2권:3660~3668)와
  **다른** 위치(2권:2182)임을 스크립트 주석에 명시 — 정답 청크 표현을 베낀 순환 논증이
  아니라는 근거가 남아 있다. D-패턴들은 스크립트 자체가 "정답 청크의 고유 표현(예:
  100g/우유/g·kg·day/슈가토스트)을 의도적으로 피했다"고 self-critique까지 적어뒀다.
  → **근거 로깅 누락 없음**, 원 태스크가 요구한 "독립적 근거"가 충족돼 있다.

## itch1 (22~23위→1위 재현 여부, 최신 KB에서)

**재현되지 않는다.** 실제 baseline은 22위(0.3810) — 이전에 캐시된 "22~23위" 주장 중
22는 일치하지만 23은 아님(정확히 22). 더 중요한 차이: 이전 "→1위" 주장은 **재현되지
않는다**. 실측 데이터(phase2_3_rewrites, phase4)는 C-rewrite("혈액투석 환자의
소양증 원인")로 22위 → gate 통과 후보 중 6위 → **최종 top5 중 3위**다. 1위가 아니라
top5 안의 3위. "최종 답변 컨텍스트에 들어가는 5개 청크 중 하나가 된다"는 점에서
실용적으로는 성공(A)이지만, 과거의 "1위 재현" 주장은 이번 정직한 재측정으로 정정한다.

## prot2 / snack1 — 개선 여부 재평가

- **prot2**: D-rewrite("...권장량 체중 기준")가 25위 → 4위로 뚜렷하게 개선되고
  production sim에서 실제로 최종 top5(4위)에 들어간다. → **원래 태스크가 예상했던
  "rewrite 무의미, chunk 문제로 재분류" 가설은 이 데이터로는 기각**된다. prot2는
  진짜로 질문 표현(단어 선택) 문제였고, 제네릭 수량 접미사 하나로 해결됐다.
- **snack1**: B/D 두 rewrite 모두 실패(368위, 209위 — 오히려 원본 225위보다 나쁘거나
  거의 그대로), 풀10 진입 근처도 못 감. → **chunk-representation/ranking 문제로
  재분류가 맞다**. 정답 청크("[슈가토스트]" 레시피, 혈액투석환자를_위한_간식)는 질문
  표현을 아무리 바꿔도 임베딩 유사도 랭킹에서 회복되지 않는다 — 청크 자체의 임베딩
  표현력(짧은 레시피 나열 vs. 질문 어휘와의 의미적 거리)이 근본 원인으로 보인다.

## fish1 (rewrite로 살리는 게 실제로 안전한가)

**아니다 — 보수적 판단을 유지한다.** 원본 질문의 top1 score조차 0.2873으로
RAG_MIN_SCORE(0.30) 미만이라, 지금은 "근거자료 없음"으로 정직하게 거절하는 상태다.
D-rewrite로 순위가 64위→55위로 소폭 개선되지만 여전히 풀10 근처에도 못 미치고,
production sim 자체가 실행되지 않을 만큼 실패다(=최종 답변에 못 들어감, 그래서
사실 이번 데이터에서는 위험한 낮은-확신 답변을 억지로 통과시키는 상황조차 발생하지
않았다). 다만 원 태스크가 요구한 원칙은 여전히 유효하다: **만약** 어떤 rewrite가
fish1의 raw score를 억지로 게이트 위로 밀어올린다 해도, 이는 "안전한 거절"을
"근거 희박한 저확신 답변"으로 바꾸는 트레이드오프이므로 점수 상승 자체를 성공으로
치지 않아야 한다. 이번 데이터에서 fish1은 D(악화/무의미) + E(설령 통과시켜도 채택
부적절) 이중 판정.

## Positive 30 (Recall@1/3/5/10, before→after, 기계적 B-패턴 전체 적용)

phase6_regression30(30/30 전부 존재, log tail과 JSON 완전 일치 확인). "before"/"after"
는 실제 production 체인(`retrieve→_relevant→_rerank`, RAG_MIN_SCORE·RAG_CONTEXT_MAX
그대로 사용)을 30문항 전원에 대해 시뮬레이션한 결과이며, rewrite는 **B-패턴 단일
고정 템플릿**("혈액투석 환자의 " + 원문)만 사용(문항별 맞춤 rewrite가 아님 — "전체
RAG 문항에 기계적으로 rewrite 적용" 시나리오를 시험하기 위해 의도적으로 단일 규칙).

| 지표 | before | after | 변화 |
|---|---|---|---|
| Recall@1 (pool10 기준) | 10/30 | 6/30 | -4 |
| Recall@3 | 13/30 | 7/30 | -6 |
| Recall@5 | 19/30 | 8/30 | -11 |
| Recall@10 (pool 진입) | 23/30 | 14/30 | -9 |
| 최종 top5(실사용 answer() 결과) | 19/30 | 11/30 | -8 |
| gate_pass(게이트만) | 29/30 | 30/30 | +1 |

개선/악화/불변 카운트(최종 top5 기준): **개선 2건**(water1, snack2) / **악화 10건**
(k2, na1, na2, prot1, eat1, fruit2, ckd1, p3, bone1, kfruit1) / **불변 18건**.

**결론: 단일 기계적 B-패턴을 30개 positive 문항 전체에 적용하면 순수하게 해롭다.**
개선보다 악화가 5배 많고, 모든 recall 지표가 절반 가까이 떨어진다. "질문 앞에
도메인 프리픽스만 붙이면 무조건 도움 된다"는 직관은 이 데이터로 명백히 반박된다.

끌어올려서, 원 질문의 실제 주제와 무관하게 게이트를 통과시킨다. 이는 "새로운
out-of-scope 응답이 하나라도 새로 게이트를 통과하면 심각한 안전 비용"이라는 원
태스크의 기준을 압도적으로 초과한다.

## 추천: **Option B — 조건부·좁은 범위 rewrite만 허용**

Option A(rewrite 불필요)는 기각 — itch1/prot2/snack2 3건은 실측으로 진짜 개선됐다.
Option C(전체 RAG 문항에 기계적 rewrite 적용)는 **강하게 기각** — 두 개의 독립적
데이터가 같은 결론을 가리킨다:
1. Positive 30문항 전체에 단일 B-패턴 적용 시 최종 top5 정답률이 19/30→11/30으로
   순감소(개선 2 : 악화 10).
2. Out-of-scope 21문항 전체가 같은 패턴에 게이트를 100% 통과 — 안전 실패.

Option D(LLM 기반 rewrite, 향후 방향으로만 플래그, 지금 구현 안 함)는 근거가 약함 —
이번 실험은 규칙 기반 rewrite만 다뤘고 LLM rewrite를 직접 시험하지 않았으므로 채택도
기각도 부적절. 다만 성공한 3건(itch1=C:임상 동의어, prot2=D:수량 프레이즈, snack2=B:
도메인 프리픽스)이 문항마다 다른 패턴에서 나왔다는 사실은, 향후 "질문 의도를 이해하고
문항별로 다른 방식으로 재구성"하는 LLM-rewrite가 규칙 기반보다 유망할 수 있음을
시사한다 — 단, 이는 구현하지 않고 방향성만 기록한다.

**채택: Option B.** 사람이 검수한 rewrite를, 실측으로 검증된 특정 hard-case
질문에만, production 시뮬레이션으로 최종 top5 진입을 사전 확인한 뒤 좁게 적용한다.
전체 문항이나 미지의 사용자 입력에는 절대 기계적으로 적용하지 않는다(Phase 5가 보여준
안전 비용이 너무 크다).

## Production 적용 시 예상 구조 (설계만, 구현 안 함)

- rewrite는 **정적 매핑 테이블**로 관리한다: `{정규화된 원 질문/질문 클러스터: rewrite
  텍스트}` — itch1/prot2/snack2 같이 실측으로 검증된 항목만 등재. 임의의 사용자 자유
  입력에 실시간으로 기계적 rewrite 규칙을 적용하지 않는다(이것이 Phase 5/6이 보여준
  실패 모드).
- retrieve 단계에서만 rewrite 텍스트를 사용하고, `_rerank()`의 어휘 보너스는 원본
  질문 텍스트로 계산한다(Phase 4에서 이미 검증된 설계 — rewrite에 섞인 범용 접미사
  단어가 어휘-중복 점수를 부풀려 무관한 청크를 유리하게 만드는 걸 방지).
- 신규 후보 rewrite를 매핑 테이블에 추가하기 전에는 반드시 (a) 해당 hard-case
  positive 질문에서 baseline→rewrite 순위 개선을 재현하고, (b) 전체 21개
  out-of-scope 세트에 대해 게이트 신규통과가 0건임을 재확인하는 회귀 테스트를
  통과해야 한다.
- 매핑에 없는 질문은 원문 그대로 기존 파이프라인을 통과한다(현재 동작 유지, 회귀
  없음).

## 메타 노트

**이전 세션이 남긴 실험 결과를 그대로(as-is) 재사용했다. 재실행하지 않았다.**
이유: `query_rewrite_experiment.py` 전문을 읽고 (1) production 코드를 import해서
그대로 체이닝하는지(`FOOK_rag_chatbot.py`의 `answer()` 함수 로직, 라인 503-510과
스크립트의 phase4/phase6 체인을 나란히 대조해 완전히 일치함을 확인했다), (2) 7개
hard case 전부 null/에러 없이 채워져 있는지, (3) 21개 out-of-scope 전부, 30개
positive 전부가 빠짐없이 채워져 있는지, (4) 각 rewrite에 사후 역설계가 아닌 사전
근거(`reasoning` 필드, grep 인용 등)가 남아있는지를 JSON/로그 교차검증으로 직접
확인했고, 전부 통과했다. 로그 tail의 "=== DONE ==="과 JSON의 5개 phase 키가 정확히
일치했으며, 로그에 찍힌 개별 라인 값(예: oos1~21의 before/after 점수, phase6의
before/after top5 여부)이 JSON 파일의 값과 1:1로 일치함을 별도로 스팟체크했다.
이 정도 일치도라면 데이터가 실제 라이브 API 호출로 생성된 것이지 조작되거나 부분
누락된 게 아니라고 판단했고, 크래시가 보고서 작성 단계(라이브 실험 이후)에서 발생했다는
전제와도 부합한다. 따라서 API 비용/시간을 들여 재실행하지 않고 이 리포트를 실측
데이터로부터 직접 종합했다. 유일하게 스크립트 실행 없이 추가로 한 작업은: 위의
독립 재계산(out-of-scope 신규통과 개수, positive 30 recall@k 집계, 분류 판단)뿐이며,
이는 모두 기존 JSON을 python으로 직접 읽어 계산한 것으로 재현 가능하다.
